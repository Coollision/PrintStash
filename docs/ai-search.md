## Implemented foundation

- A pure, versioned text recipe in `printstash-core.search.passages`.
- Source extraction for Models, Collections, Multipart Models and Documents in
  `search.sources`. Model tags use the existing effective-tag owner; source
  descriptions use the provenance owner's effective-value rule.
- Durable `search_passages`, with a unique Subject/segment/window/recipe identity,
  an explicit truncation flag and a content watermark.
- `search.passages.sync_subject(session, subject)`, an internal operation that
  stages and flushes passage changes in the caller's transaction. It never
  commits, performs inference or reads binary document bodies. Callers must
  serialize concurrent writes to the same Subject.
- An additive autogenerated migration. Existing inference spaces, generations
  and vectors remain available for the later W3/W12 adoption work.

There is no automatic indexing or new search endpoint in this increment. The
existing browse/search behavior continues to run. No inference model is selected
or acquired, and no library content is sent to an endpoint.

## Recipe v1

The stable field order is title, Collection path, effective tags, filenames,
Revision text, source titles, source summaries, source tags, Multipart Parts,
Model Choices, description and Markdown body. Empty fields are omitted; metadata
whitespace is collapsed and text is normalized to Unicode NFC. The source
summary comes from the effective provenance description. Binary Documents
contribute their name and filename only.

| Bound | Recipe-v1 value |
| --- | --- |
| Metadata entries per field | 64 |
| Characters per metadata field | 4,096 |
| Metadata budget per Passage | 8,192 characters |
| Durable body budget before splitting | 131,072 characters |
| Body window | 400 Unicode words/punctuation units |
| Window overlap | 40 units |
| Windows per Visibility Segment | 16 |
| Characters per complete Passage | 16,384 |

These are deterministic **recipe units**, not an inference model's tokenizer.
W4/W7 must enforce and report their provider's token limits separately. Metadata
is repeated in every window, with a separate body budget. Exceeding a text,
window or cardinality cap sets `truncated`; it never silently claims a complete
projection. Changing the field list, normalization or limits requires a new
recipe version.

Multipart member names and imported choice labels each belong to a segment
requiring that member Model's permission in addition to the Multipart Subject's
permission. They are never merged into the grouping's shared text. Stored
dependency identities do not grant access: retrieval must authorize both the
Subject and every contributor immediately before use, including before ranking,
highlighting or composing the response.

Identical text retains its Passage ID, content hash and content watermark.
Unrelated Model edits do not invalidate content. Refreshing a live Subject
replaces only the current recipe; removing a missing or trashed Subject removes
all its recipes. Multipart Models currently use hard deletion, and follow the
missing-Subject path.

## Next W1 work

1. Define the neutral injected projection port and bind it in bootstrap. Invoke
   it inside every relevant content transaction, covering relation deletions and
   ancestor changes as well as direct Subject edits.
2. Add the dependency inventory and bounded, durable reconciliation sweep.
   `source_updated_at` alone is insufficient: Collections have no modification
   timestamp, and Artifact notes and tag links can change without touching their
   Model's timestamp.
3. Preserve every recipe needed by active/building Generations and connect
   content invalidation to their durable work selection when W3/W5 exists.
4. Add the synchronous lexical projection at W2 and the authorized read seam.
   Until then, stored Passages are internal data, not a result API.
