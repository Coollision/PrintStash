## Implemented foundation

- A pure, versioned text recipe in `printstash-core.search.passages`.
- Source extraction for Models, Collections, Multipart Models and Documents in
  `search.sources`. Model tags use the existing effective-tag owner; source
  descriptions use the provenance owner's effective-value rule.
- Durable `search_passages`, with a unique Subject/segment/window/recipe identity,
  an explicit truncation flag and a content watermark.
- `search.passages.sync_subject(session, subject)`, an internal operation that
  stages and flushes passage changes in the caller's transaction. It never
  commits, performs inference or reads binary document bodies. Callers must
  serialize concurrent writes to the same Subject.
- Neutral projection and ranked-read ports. Content owners update passages and
  lexical statistics in their own transaction; bootstrap binds the adapters.
- Bounded durable watermark, rolling source and orphan repair, paused during
  restore maintenance and drained on shutdown.
- Weighted SQLite FTS5 and PostgreSQL BM25. PostgreSQL uses a managed generated
  tsvector/GIN candidate index plus transactional postings, document frequencies
  and corpus lengths. It does not relabel `ts_rank` as BM25.
- `GET /api/v1/search`, authorized before ranking for each Subject and every
  contributing segment, with plain-text evidence and signed query-context
  cursors. Model cards reuse the library's authorized projection owner.
- Ranked Model browse through the neutral read port, including cursor pages.
- Additive autogenerated migrations with SQLite/PostgreSQL upgrade tests.

The base search is usable without AI. A missing or failed FTS index falls back
on escaped, ranked LIKE over durable passages. Its rebuild visits bounded pages;
content mutations continue while the native index is unavailable. No inference
model is selected or acquired at this stage.

The lexical recipe weights title 5, tags 3 and full text 1. BM25 uses k1=1.2,
b=0.75 and FTS5's positive IDF floor. Query syntax is literal Unicode words,
limited to 512 characters and 32 distinct terms. Punctuation is a separator;
terms over 128 characters are omitted from portable postings. These are not
stemming or typo-tolerance promises. Technical references are
[SQLite FTS5](https://sqlite.org/fts5.html#the_bm25_function) and
[PostgreSQL text-search ranking](https://www.postgresql.org/docs/16/textsearch-controls.html#TEXTSEARCH-RANKING).

## Recipe v1

The stable field order is title, Collection path, effective tags, filenames,
Revision text, source titles, source summaries, source tags, Multipart Parts,
Model Choices, description and Markdown body. Empty fields are omitted; metadata
whitespace is collapsed and text is normalized to Unicode NFC. The source
summary comes from the effective provenance description. Binary Documents
contribute their name and filename only.

| Bound | Recipe-v1 value |
| --- | --- |
| Metadata entries per field | 64 |
| Characters per metadata field | 4,096 |
| Metadata budget per Passage | 8,192 characters |
| Durable body budget before splitting | 131,072 characters |
| Body window | 400 Unicode words/punctuation units |
| Window overlap | 40 units |
| Windows per Visibility Segment | 16 |
| Characters per complete Passage | 16,384 |

These are deterministic **recipe units**, not an inference model's tokenizer.
W4/W7 must enforce and report their provider's token limits separately. Metadata
is repeated in every window, with a separate body budget. Exceeding a text,
window or cardinality cap sets `truncated`; it never silently claims a complete
projection. Changing the field list, normalization or limits requires a new
recipe version.

Multipart member names and imported choice labels each belong to a segment
requiring that member Model's permission in addition to the Multipart Subject's
permission. They are never merged into the grouping's shared text. Stored
dependency identities do not grant access: retrieval must authorize both the
Subject and every contributor immediately before use, including before ranking,
highlighting or composing the response.

Identical text retains its Passage ID, content hash and content watermark.
Unrelated Model edits do not invalidate content. Refreshing a live Subject
replaces only the current recipe; removing a missing or trashed Subject removes
all its recipes. Multipart Models currently use hard deletion, and follow the
missing-Subject path.

## Remaining implementation

The W1/W2 stage gate passed 3,264 repository, integration and end-to-end tests.
Separate PostgreSQL checks passed seven migration, BM25 and authorization tests;
the native-table-loss browse regression passed with its 18-test focused gate.
These results cover the text foundation, not the unimplemented AI stages below.

W3/W5 will retain every recipe needed by active/building generations and connect
content invalidation to durable embedding work. Existing inference spaces,
generations and vectors are the adoption point; the feature will not introduce
a parallel vector store. W4/W4b add the remote embedding and chat contracts.
Local model acquisition, hybrid retrieval, UI, visual profiles, captions, sparse
expansion, quantization and natural-language filters remain in progress.

The [coverage matrix](ai-search-coverage.md) retains all 142 original planned
behaviors and the independently verified passage/lexical subcontracts. Full
feature readiness also requires the remaining stages, feasibility evidence and
a security diff scan of the completed branch.
